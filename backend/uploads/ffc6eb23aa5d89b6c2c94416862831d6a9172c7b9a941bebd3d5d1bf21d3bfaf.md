# 大模型/RAG 高频面试题全解

------

## 一、基础概念高频题

------

### 1. RAG 的完整执行流程？每一步的作用是什么？

RAG（Retrieval-Augmented Generation，检索增强生成）分为 **离线索引阶段** 和 **在线问答阶段** 两大阶段：

#### 📌 离线索引阶段（知识库构建，只做一次/定期更新）

| 步骤                               | 作用                                                    |
| ---------------------------------- | ------------------------------------------------------- |
| **① 数据加载（Document Loading）** | 读取 PDF、Word、网页、数据库等多源数据                  |
| **② 文档清洗与解析**               | 去除噪声（页眉页脚、乱码），统一格式                    |
| **③ 文本分片（Chunking）**         | 将长文档切成合适大小的片段，便于检索和匹配              |
| **④ 向量化（Embedding）**          | 用 Embedding 模型将每个文本块转为高维向量               |
| **⑤ 存入向量数据库**               | 将向量和原文存入 Milvus/Chroma/FAISS 等向量库，建立索引 |

#### 📌 在线问答阶段（用户每次提问触发）

| 步骤                          | 作用                                              |
| ----------------------------- | ------------------------------------------------- |
| **⑥ 用户问题向量化**          | 用同一个 Embedding 模型将 query 转为向量          |
| **⑦ 相似度检索（粗召回）**    | 在向量库中做 ANN 近似搜索，召回 Top-K 相关片段    |
| **⑧ Reranker 重排序（精排）** | 用 Cross-Encoder 等模型对召回结果精排，提升相关性 |
| **⑨ 构建 Prompt**             | 将检索到的上下文 + 用户问题组装成完整 Prompt      |
| **⑩ LLM 生成回答**            | 大模型基于上下文生成最终答案                      |

> **一句话总结**：先建库（索引），再查库（检索），最后让模型"开卷考试"（生成）。

### 2. 大模型幻觉是什么？如何有效抑制？

**幻觉（Hallucination）** 指模型生成看似流畅、自信，但实际上**与事实不符或完全编造**的内容。

**产生原因：**

- 训练数据中存在噪声/错误
- 模型本质是"概率续写"，不真正"理解"事实
- 知识截止日期后的信息盲区
- 解码时 temperature 过高导致随机性增强

**抑制手段（由易到难）：**

| 方法                  | 说明                                         |
| --------------------- | -------------------------------------------- |
| **RAG 检索增强**      | 给模型提供事实依据，要求"只根据给定材料回答" |
| **Prompt 约束**       | 加入"如果不确定请回答'不知道'"等指令         |
| **降低 temperature**  | 减少生成随机性（如设为 0~0.3）               |
| **事实核查/引用溯源** | 要求模型标注信息来源，人工或自动验证         |
| **Fine-tuning 对齐**  | 用 RLHF/DPO 让模型学会拒绝回答               |
| **多模型交叉验证**    | 用另一个模型审核第一个模型的输出             |
| **知识图谱约束**      | 将结构化知识注入，限制生成范围               |

------

### 3. Prompt 工程有哪些常用优化技巧？

| 技巧                           | 说明                                     |
| ------------------------------ | ---------------------------------------- |
| **角色设定（Role Prompting）** | "你是一位资深法律顾问…" 激活模型相关能力 |
| **明确指令 + 约束**            | 清晰说明任务、格式、字数、禁止事项       |
| **Few-shot 示例**              | 给 2~5 个输入输出示例，引导模型模仿      |
| **Chain-of-Thought（CoT）**    | "请一步步思考"，引导推理过程             |
| **分步拆解任务**               | 复杂任务拆成多个子 Prompt 串联           |
| **输出格式约束**               | 要求 JSON/Markdown/表格等结构化输出      |
| **负面约束**                   | "不要编造信息""不要输出无关内容"         |
| **温度与采样参数调节**         | temperature、top_p 控制创造性 vs 确定性  |
| **迭代优化（Prompt Tuning）**  | 根据错误案例反复调整 Prompt 措辞         |

------

### 4. 微调、RAG、Prompt 优化三者的区别和适用场景？

| 维度             | Prompt 优化            | RAG                        | 微调（Fine-tuning）          |
| ---------------- | ---------------------- | -------------------------- | ---------------------------- |
| **本质**         | 不改模型，只改输入指令 | 外挂知识库，检索后生成     | 修改模型权重                 |
| **成本**         | 极低                   | 中等（需维护知识库）       | 高（需 GPU + 数据标注）      |
| **见效速度**     | 即时                   | 快（更新文档即可）         | 慢（需重新训练）             |
| **适用场景**     | 通用任务调优、格式控制 | 知识密集型问答、时效性信息 | 特定风格/领域/格式的深度定制 |
| **典型例子**     | 让模型输出 JSON        | 企业知识库问答             | 医疗/法律垂直领域模型        |
| **是否更新知识** | ❌                      | ✅ 实时更新                 | ⚠️ 需重新训练                 |

> **选择优先级**：Prompt 优化 → RAG → 微调（成本递增，先轻后重）

## 二、项目实战高频题

------

### 5. 文本为什么需要分片？分片大小如何设置？

**为什么分片：**

- Embedding 模型有最大 token 限制（通常 512~8192 tokens）
- 长文档直接检索会导致语义稀释，匹配不精准
- LLM 上下文窗口有限，不能把整本书塞进去
- 分片后可并行处理，提升检索效率

**分片策略与大小设置：**

| 策略             | 说明                                       |
| ---------------- | ------------------------------------------ |
| **固定大小分片** | 如 512 tokens/块，简单但可能截断语义       |
| **递归字符分片** | 按段落→句子→字符逐级切分（LangChain 默认） |
| **语义分片**     | 基于语义相似度变化点切分，效果最好但最慢   |
| **结构化分片**   | 按标题/章节/表格等文档结构切分             |

**大小设置经验：**

- 一般 **256~1024 tokens**（中文约 200~800  字）
- **overlap（**重叠部分**） 设 10%~20%**（如 chunk=512，overlap=50~100），防止边界信息丢失
- 问答场景偏小（256~512），摘要场景偏大（512~1024）
- 需要根据实际检索效果做 A/B 测试调优

### 6. 检索召回不准确、匹配度低怎么优化？

**排查思路：从 Query → 检索 → 排序 → 数据 逐层排查**

| 优化方向                      | 具体方法                                                     |
| ----------------------------- | ------------------------------------------------------------ |
| **Query 改写**                | 用 LLM 将口语化问题改写为关键词/专业表述；Query Expansion 扩展多个子查询 |
| **混合检索（Hybrid Search）** | 向量语义检索 + BM25 关键词检索，用 RRF 融合排序              |
| **更换/微调 Embedding 模型**  | 中文场景用 BGE-M3、M3E 等；领域数据微调 Embedding            |
| **增加 Reranker 精排**        | 粗召回 Top-20 → Cross-Encoder 精排取 Top-5                   |
| **优化分片策略**              | 减小 chunk size、增加 overlap、按语义切分                    |
| **元数据过滤**                | 给文档加标签（来源/时间/类别），检索时先过滤再匹配           |
| **多路召回**                  | 同时用摘要向量、原文向量、关键词索引多路检索                 |
| **数据质量**                  | 清洗噪声、去重、补充同义词/缩写映射                          |

### 7. 项目中遇到的最大难点是什么？怎么解决的？

> （这是一道开放题，以下提供**高分回答模板**）

**参考回答结构（STAR 法则）：**

> **难点示例**：多格式文档（PDF 表格 + 扫描件 + 图文混排）解析质量差，导致检索召回率低。

- **Situation**：知识库包含大量扫描版 PDF 和复杂表格，OCR 识别率低，表格结构丢失

- **Task**：需要让检索系统准确召回表格中的数据

- Action

  ：

  1. 引入专业文档解析工具（如 Unstructured / PaddleOCR）处理扫描件
  2. 表格单独抽取为结构化 JSON，附加元数据标记
  3. 对表格内容做"自然语言化"描述，再生成向量
  4. 增加关键词检索作为补充（表格中的数字/专有名词适合精确匹配）

- **Result**：召回率从 60% 提升到 90%+

### 8. 如何提升大模型问答的准确率和响应速度？

| 维度         | 方法                                                         |
| ------------ | ------------------------------------------------------------ |
| **准确率**   | ① 优化检索质量（混合检索 + Rerank）② Prompt 中加入"仅根据以下内容回答"③ 增加 Few-shot 示例④ 答案后处理 + 事实核查 |
| **响应速度** | ① 向量检索用 HNSW/IVF 索引加速② 减少 Top-K 数量（如 5→3）③ 流式输出（Streaming）降低用户感知延迟④ 缓存高频问答结果⑤ 模型量化（INT8/INT4）或换用轻量模型⑥ 异步并发处理 |
| **体验**     | 先展示"正在检索…"，再流式输出答案；对超时做兜底回复          |

## 三、框架与工具高频题

------

### 9. LangChain 的核心组件有哪些？各自作用？

| 组件                | 作用                                                     |
| ------------------- | -------------------------------------------------------- |
| **Model I/O**       | 统一封装 LLM / Chat Model / Embedding Model 的调用接口   |
| **Prompt Template** | 管理和模板化 Prompt，支持变量填充                        |
| **Document Loader** | 加载 PDF、Word、网页、CSV 等 100+ 种数据源               |
| **Text Splitter**   | 文档分片（递归切分、语义切分等）                         |
| **Embedding**       | 文本向量化（对接 OpenAI / HuggingFace / 本地模型）       |
| **Vector Store**    | 向量存储与检索（Chroma / FAISS / Milvus / Qdrant…）      |
| **Retriever**       | 检索器抽象，支持向量检索、BM25、混合检索、Multi-Query 等 |
| **Chain / LCEL**    | 将多个步骤串联为流水线（LangChain Expression Language）  |
| **Agent**           | 让 LLM 自主决策调用工具（搜索、计算、代码执行等）        |
| **Memory**          | 对话记忆管理（短期/长期/摘要记忆）                       |
| **Output Parser**   | 将 LLM 输出解析为结构化数据（JSON/Pydantic）             |
| **Callback**        | 日志、监控、流式输出等钩子机制                           |

### 10. 向量数据库的作用是什么？为什么不用普通数据库？

**作用：**

- 存储文本的高维向量表示（如 768/1024/1536 维）
- 支持高效的**近似最近邻搜索（ANN）**，实现语义级相似度匹配
- 为 RAG 提供毫秒级检索能力

**为什么不用普通关系型数据库（MySQL/PostgreSQL）？**

| 对比维度               | 向量数据库                                        | 普通数据库                 |
| ---------------------- | ------------------------------------------------- | -------------------------- |
| 检索方式               | 语义相似度（余弦/内积/L2）                        | 精确匹配 / LIKE 关键词     |
| "苹果手机" vs "iPhone" | ✅ 能匹配（语义相近）                              | ❌ 无法匹配                 |
| 高维计算               | 专为 ANN 优化（HNSW/IVF/PQ）                      | 无此索引结构，全表扫描极慢 |
| 百万级查询延迟         | 毫秒级                                            | 秒级甚至不可用             |
| 典型代表               | Milvus、Chroma、FAISS、Qdrant、Weaviate、Pinecone | MySQL、MongoDB             |

> **补充**：PostgreSQL + pgvector 插件可以做轻量级向量检索，适合小规模场景；大规模生产仍推荐专用向量数据库。

### 11. 本地部署开源模型和调用 API 的区别？优缺点？

| 维度         | 本地部署开源模型                                  | 调用云端 API                              |
| ------------ | ------------------------------------------------- | ----------------------------------------- |
| **典型代表** | LLaMA、Qwen、ChatGLM、Mistral（Ollama/vLLM 部署） | GPT-4、Claude、通义千问 API、文心一言 API |
| **数据隐私** | ✅ 数据不出内网，适合敏感行业                      | ⚠️ 数据上传至第三方，有合规风险            |
| **成本**     | 前期 GPU 硬件投入高，后期边际成本低               | 按 token 计费，量大费用高                 |
| **灵活性**   | 可微调、可定制、可控推理参数                      | 黑盒，无法修改模型权重                    |
| **部署难度** | 需要运维团队、GPU 资源、模型优化                  | 开箱即用，SDK 接入即可                    |
| **性能上限** | 受限于本地算力（7B~72B）                          | 可用最强模型（如 GPT-4 级别）             |
| **响应速度** | 取决于硬件，可优化（量化/批处理）                 | 依赖网络延迟 + 服务商并发                 |
| **适用场景** | 金融/医疗/政务等数据敏感场景；离线环境            | 快速验证、中小规模应用、追求最强效果      |

> **面试加分回答**：实际项目中常采用**混合架构**——敏感数据走本地小模型，复杂推理任务走云端大模型 API，兼顾安全与效果。

## 📋 面试回答小贴士

1. **结构化表达**：先总后分，用"第一/第二/第三"或表格
2. **结合项目**：每个技术点尽量关联自己的实际经验
3. **说出权衡**：不只说"怎么做"，还要说"为什么这样做"以及"还有什么替代方案"
4. **数据说话**：如"优化后召回率从 60% 提升到 92%"比"效果变好了"更有说服力
